# Content-Addressed Storage Design — Retiring exports/

A design that **retires** the human-readable `exports/` layer from the storage layout in
`docs/dev/thinkingface-design.md` §4, making GCS keys fully independent of namespace,
repository name, and ref. The predecessor was `docs/single-copy-storage-design.md`
(deleted — a design that promoted `exports/` to be the "real" copy and eliminated the
double-holding with `lfs/`). This design does not continue that line; instead it solves
the same double-holding problem by **eliminating the concept of exports/ altogether**.

Among the externally visible contracts, the biggest difference from the predecessor is
**what changes**:

- ~~`gcloud storage cp -r gs://…/exports/datasets/ns/name/main/`~~ no longer works.
  Instead, run the script generated by `GET /api/v1/repos/{kind}/{ns}/{name}/gcs/{rev}`
- BigQuery external tables and DuckDB's `read_parquet('gs://…')` work as long as they
  know the object's `gs://` URI, so only the way you **obtain** the URI changes — the
  functionality itself is unchanged
- git clone / LFS pull / the HF-compatible API are unrelated and unchanged

## 1. Goals and Non-Goals

### Goals

- **Move zero GCS-object bytes on transfer, rename, or delete.** The prior design
  (`docs/dev/repo-transfer-design.md`) decoupled the WAL and the bare repository from the
  name via `storage_path`, while `exports/` alone stayed bound to the `(ns, name)` key for
  the sake of human-readable paths, requiring a relocation job (`relocate_exports`) on
  every transfer. This eliminates that asymmetry
- **Simplify the mechanism.** The predecessor design (`docs/single-copy-storage-design.md`)
  carried the complexity that "the same key might be the real copy, so both deletes and
  overwrites require evacuating it first" (the `vacateExportKey` / `relocateIfHome` /
  `reconcileLFSHome` trio). Once the location of the real copy is decoupled from the
  repository name, there is no longer any room for this complexity to arise
- **Make deduplication complete.** In the predecessor design, the real copy per oid still
  converged to one, but because "the real copy on the default branch lives at
  `exports/{ns}/{name}/...`," two repositories whose default branches happened to hold a
  file with identical content ended up with two real copies (only one was deterministically
  chosen as the "home"; the other held an independent copy at its own `exports/` path).
  Unifying everything under a single content-addressed key removes this last form of
  duplication too

### Assumptions

**There is no concept of repository visibility (public / private).** We deliberately
treat this as a single-tenant, internal-only system where every repository is equally
readable by everyone. This design depends on that: visibility plays no role in deciding
what gets published to `blobs/`, so any pushed ref may be published unconditionally.

**Because this targets production readiness, there is no consideration for backward
compatibility with existing data.** The DB and the bucket are assumed to be rebuilt from
scratch, and the design takes the shortest path on that assumption (§7).

### Non-Goals

- The external shape of the HF-compatible endpoints, the LFS batch API, and git smart
  HTTP is unchanged
- The key layout and protocol of `wal/` is unchanged (`docs/dev/continuity-design.md`)
- Bulk retrieval of a whole directory (`cp -r`) or glob-based prefix selection is **not**
  restored by this design. What is lost and its replacement are covered in §8

## 2. New Layout

```
gs://{bucket}/
├── lfs/{oid[0:2]}/{oid[2:4]}/{oid}          The single home for LFS real copies. Content-addressed,
│                                             immutable, deduplicated across repositories
│                                             (storage.LFSKey)
├── blobs/{sha[0:2]}/{sha[2:4]}/{sha}        Real copies of non-LFS git blobs. The Sync Worker
│                                             publishes every file of every pushed ref (all
│                                             branches/tags).
│                                             Content-addressed, immutable (storage.BlobKey).
│                                             The viewer cache (formerly cache/blobs/{sha}) is
│                                             folded into this same key
├── wal/{storage_path}/…                      Unchanged (docs/dev/continuity-design.md)
└── tmp/uploads/…                              Unchanged
```

`exports/` and `cache/blobs/` disappear. The bucket retains **no human-readable elements
whatsoever** — you cannot tell which repository an object belongs to just by looking at
its key. The human-readable mapping does not live in GCS at all; the API computes it on
demand in the form of the `GET .../gcs/{rev}` response (§6).

## 3. Invariants

```
I1. Every LFS oid has its real copy only at storage.LFSKey(oid). It exists at no other key
I2. Every non-LFS git blob sha, once published, has its real copy only at
    storage.BlobKey(sha)
I3. Both keys are immutable. Writes are "create if absent" only — no overwrite,
    move, or rename ever happens
```

The predecessor design's `lfs_objects.storage_key` (a pointer column indicating whether
the real copy lived under `lfs/` or `exports/`) is **retired**. The location of the real
copy can always be derived from the oid via `storage.LFSKey(oid)`, and there is no longer
any set of "multiple candidates" that would need pointing to in the first place. The
resolution layer built around it — `store.LFSStorageKey` / `LFSStorageKeys` /
`PreferredLFSHome` / `SetLFSStorageKey` — becomes unnecessary as well.

Reflecting that, the current schema (`internal/store/migrations/postgres/0001_init.sql`,
`migrations/sqlite/0001_init.sql`) simply does not have these:

```
-- lfs_objects has no storage_key column (and no idx_lfs_objects_storage_key index).
-- That column used to track whether the real copy had moved between lfs/ and
-- exports/; now that the real copy's address is fixed by the oid alone, tracking
-- it is unnecessary.

-- storage_reclaim_jobs does not exist. It used to be a queue for asynchronously
-- deleting the exports/ tree after a repository was deleted. Deletion no longer
-- touches GCS at all, so it's unnecessary (folded into thinkingface gc).

-- sync_jobs never carries a kind = 'relocate_exports' row. That job used to
-- relocate exports/ to a new prefix on transfer; the corresponding pipeline no
-- longer exists.
```

`lfs_objects` becomes just `(oid PRIMARY KEY, size, created_at)`.

## 4. Sync Worker (`internal/syncer`)

The comment at the top of the package is itself a summary of the design:

> Storage is two content-addressed layers and nothing else: LFS bytes at
> `storage.LFSKey(oid)`, plain git blobs at `storage.BlobKey(sha)`. Both are
> immutable and deduplicated instance-wide, so a push only ever *adds* objects
> — there is no mirror to prune, no key to vacate, and transferring, renaming
> or deleting a repository moves nothing at all.

- **LFS files require no action on the storage side.** Regardless of which path uploaded
  them (an LFS batch upload or the HF preupload proxy), the real copy is written directly to
  `storage.LFSKey(oid)`, so there is nothing to re-copy after a push. What the Worker does
  maintain is the `repo_lfs_objects` link table -- the reference count §5's "Unreferenced"
  GC pass reads. `LinkLFSObjects` adds a link for every oid a commit names (the HF-compatible
  commit handler calls it for one commit's pointers; the syncer's post-push pipeline calls it
  again for the whole indexed revision) and stamps that link's `committed_at`, marking it as
  confirmed rather than merely uploaded.
  **`store.PruneRepoLFSLinks`** (called from `Syncer.pruneLFSLinks`, after the file index for
  the pushed ref has been rebuilt and once the repository's sync queue is quiet) removes
  **only the links no commit has ever named** (`committed_at IS NULL`), gated by a 24h age
  floor (`lfsLinkGrace`) for the same reason the `blobs/` grace period below exists -- a link
  can be younger than the commit that will reference it. In practice that is one thing: an LFS
  transfer that completed and whose commit never arrived (a `tf up` or `huggingface_hub`
  upload interrupted between the upload and the commit).
  - **This deliberately does not touch history.** An earlier revision of this pass instead
    reconciled a repository's links against `repo_files` -- which holds one row per file of
    each *ref tip* -- releasing every link no current tip named any more. That broke `git
    checkout <old sha>`, `git lfs fetch --all`, and `resolve` at a historical revision: an LFS
    file deleted from the tip, or one that only ever existed on an older commit, lost its
    entitlement (`store.RepoHasLFSObject`) even though the commit that names it was still
    reachable, and `thinkingface gc` would then delete the bytes for real. `committed_at`
    (migration `0002_repo_lfs_link_lifecycle.sql`, which adds the link's `created_at`
    alongside it) fixed this: an object any commit ever named now keeps
    its link for as long as the repository exists, matching what git and the HuggingFace Hub
    both do. Existing rows were stamped rather than left `NULL` at migration time, so an
    abandoned upload from before the migration is not retroactively collectable -- the safe
    reading of "unknown" is "keep."
  - **The consequence, stated plainly: deleting a file does not reduce a namespace's usage.**
    `UsageByRepo` sums these links and `NamespaceQuotaForRepo` divides by that sum, and none of
    those numbers move when a file is deleted from the tip, because the commit that added it is
    still in the repository's history and cloning that revision still has to work. This is not
    a leak an earlier revision of this pass tried to fix reappearing -- it is the correct
    accounting for a versioned store, the same one `git clone` costs you. Deleting the whole
    repository, or rewriting history to drop the commits that reference the object and then
    running `thinkingface gc`, is what actually frees the bytes. See the
    `TF_DEFAULT_STORAGE_QUOTA_BYTES` row in `docs/users/self-hosting/configuration.md` for the
    user-facing version of this
- **`publishBlobs`** publishes the non-LFS files of a pushed ref to `blobs/`
  (`internal/syncer/syncer.go`). The per-file "Stat, and Put if absent" logic is unified
  into `gitrepo.Repo.PublishBlob`; other code paths that need to read an unpublished
  revision before the Worker gets to it (the parquet viewer, the experiment indexer) fill
  gaps using this same function. Because we **publish first and write `repo_files`
  afterward** (`ReplaceRepoFiles` runs only after publishing completes), the invariant "a
  row exists in `repo_files` ⇒ that blob exists in `blobs/`" always holds. What gets
  published is decided not by the old..new diff of the push but by **shas absent from the
  ref's previous index (`ListIndexedBlobSHAs`)**. Even when jobs for the same ref race, or
  an earlier job dies partway through, the job that writes the index last ends up
  publishing "everything the previous index didn't cover," so nothing slips through:
  - The target is **every pushed ref** (not limited to the default branch — branches and
    tags are both processed when pushed. The old `exports/` covered only the default
    branch)
  - When the diff (`changedPaths`) is known, only that range is processed; when it isn't
    (e.g. on an initial push), the whole tree is processed
  - For each file, `Stat` is checked first and the file is skipped if the key already
    exists. If absent, the git blob is read and `Put` (with a fixed
    `Content-Type: application/octet-stream` — since the key itself may hold the content
    of a file with any extension, no path-derived Content-Type is attached)
  - **Nothing is ever deleted.** Even if a file disappears in some commit, the `blobs/`
    object for that sha stays put (some other branch, tag, or repository might still
    reference the same content). Reclamation is the job of reference-counting GC (§5)

## 5. Reference-Counting GC (`thinkingface gc`)

Both `lfs/` and `blobs/` are layers that "disappear once nothing references them," and
neither carries an age-based bucket lifecycle rule (§9). `thinkingface gc` reclaims both
with the same command.

- **`lfs/` side**: two passes, because the layer leaks in two shapes.
  - **Unreferenced** (`gcLFSUnreferenced`): among all oids in `lfs_objects`, any that appear
    in no repository's `repo_lfs_objects` are detected as orphans. This is what makes §4's
    `PruneRepoLFSLinks` load-bearing for this pass rather than just for usage/quota
    accounting: an oid a repository deleted only becomes visible here once its link is
    pruned. Deletion is done by
    `store.DeleteOrphanedLFSObject`, which `FOR UPDATE`-locks the `lfs_objects` row and then
    deletes storage before the row (to re-check, while holding the lock, whether some other
    push/verify has just added a reference)
  - **Untracked** (`gcLFSUntracked`): an object with **no `lfs_objects` row at all**, which
    a pass that enumerates rows cannot see by construction. Every write path stores the
    bytes at `storage.LFSKey(oid)` *before* it records the row — deliberately, since the
    reverse order would advertise a row promising bytes that are not there, which nothing
    repairs — so a crash or a failed request in between (LFS verify's `promote`, the
    emulator proxy upload, `POST /api/v1/upload`, the experiment flusher) strands an object
    no query names. This pass therefore Lists the `lfs/` prefix the way the blobs side does,
    treats `lfs_objects` as the reference set (`store.UntrackedLFSObjects`), and skips keys
    that are not the canonical `LFSKey` of the oid in their basename
    - **A 24-hour grace period (`untrackedLFSGrace`)**, for the same reason `blobGrace`
      exists: an object whose row is about to be written looks exactly like one whose row
      never will be
    - **The grace is not what makes it safe, though.** Unlike a blob, an untracked `lfs/`
      object is *live*: an upload batch that Stats it present deduplicates against it and
      links the oid **without rewriting anything**, so the row can appear at any moment
      while the object's storage timestamp stays as old as it ever was — no age threshold
      can anticipate that. Deletion therefore goes through
      `store.DeleteUntrackedLFSObject`, which **claims the oid by inserting the row it is
      about to delete** (`INSERT … ON CONFLICT DO NOTHING RETURNING oid`) and holds it for
      the storage delete. A concurrent `RecordLFSObject` either committed first — in which
      case nothing is returned and the collector skips the object — or blocks on that tuple
      and afterwards fails its own `confirmPresent` check with `ErrLFSObjectGone`, which
      the batch path turns back into an upload action. This is the same protocol the
      unreferenced pass gets from `SELECT … FOR UPDATE`, obtained the only way available
      when the row whose absence *is* the condition has to be locked
    - Unlike the blobs side, **a deleted `lfs/` object is not automatically restored**:
      nothing republishes it the way the next push republishes a blob, so a client has to
      upload the content again. That asymmetry is why this pass locks rather than relying
      on the residual-window argument the blobs side accepts
- **`blobs/` side**: there is no corresponding DB table (no row records the mere existence
  of a `blobs/` object), so `repo_files.blob_sha` (rows where `lfs_oid IS NULL`, i.e.
  non-LFS files) is used as the reference count. The `blobs/` prefix in the bucket is
  Listed, and any sha absent from the reference set becomes an orphan candidate
  - **The reference set is read after the List** (`ListReferencedBlobSHAs`), so that a push
    completed while the List itself was still in progress isn't missed. The pure function
    for the decision is `store.OrphanedBlobs` (placed alongside the LFS-side
    `store.OrphanedLFSObjects`)
  - **A mandatory 24-hour grace period (`blobGrace`).** Because no row records when a
    `blobs/` object was written, "no reference exists" is always only an inference. Objects
    updated within the last 24 hours are left untouched, since we cannot rule out that they
    belong to a push whose `repo_files` commit hasn't landed yet, or to a cache the viewer
    just wrote
  - Even combining these two safeguards leaves a residual window (a push that arrives
    between the post-List re-read and the delete, for a sha that had already gone orphan
    more than 24 hours earlier) — this is accepted as tolerable. **A lost blob is not
    permanently lost**: the next push that includes that sha causes `publishBlobs` to
    republish it
- The `--dry-run` (default `true`) / `--yes` convention is shared by every pass

## 6. New API: `GET /api/v1/repos/{kind}/{ns}/{name}/gcs/{rev}`

Instead of keeping a human-readable mapping in GCS, this endpoint builds one on demand
from `repo_files` (the index for that ref, rebuilt by the sync worker on every push). The
authoritative types and response shape live in `docs/dev/api-contract.md` §2; the key points:

```ts
type RepoGCSResponse = {
  ref: string
  files: { path: string; size: number; lfs: boolean; uri: string }[]
  gcloud_script: string     // A POSIX shell script listing gcloud storage cp calls
  duckdb_snippet: string    // Non-empty only when there is at least one .parquet file
}
```

- Because everything is content-addressed, `files[].uri` is either `gs://bucket/lfs/…` or
  `gs://bucket/blobs/…`
- `gcloud_script` reproduces `path` as-is under the `DEST` environment variable (default
  `./{name}`; a `gs://` prefix may also be given). **The human-readable layout is
  generated here for the first time** — it never once existed inside the bucket
- `duckdb_snippet` passes the URIs of files that include `.parquet` directly into
  `read_parquet([...])`

Because `repo_files` is authoritative, the response matches exactly "what has actually
been published to object storage" (it does not answer based on what files git itself says
ought to exist).

The Web UI's "Fetch via GCS" dialog on each repository/file-tree page shows this response
as-is. It is the successor to the role formerly played by
`RepoDetail.gcs_uri` / `gcloud_command` (now removed).

## 7. `TreeEntryUI.gcloud_command`

Each entry in the file-tree UI
(`GET /api/v1/repos/{kind}/{ns}/{name}/tree/{rev}/{path...}`) also carries a
`gcloud storage cp '<gs://…>' './<name>'` for fetching that single file
(`apitypes.TreeEntryUI.GcloudCommand`). This is independent of the dedicated endpoint in
§6, so a screen already showing the tree can copy a file directly without going through
it. We return a ready-made command rather than a bare URI so that the shell-quoting rules
(`shellSingleQuote`, `internal/api/gcs.go`) live in the same single place as the script
generator.

Rules:

- **LFS files**: always the `lfs/` URI. Because it is content-addressed and exists
  independent of the repository, it is guaranteed no matter what `rev` is
- **Non-LFS files**: the `blobs/` URI only when the blob's sha appears in the index for
  `rev` (`repo_files`, `store.ListIndexedBlobSHAs`). Because the Worker publishes to
  `blobs/` before writing `repo_files`, the index itself is the record of "already
  published," so this looks at the same source of truth as the §6 endpoint. **It cannot be
  guaranteed — and becomes the empty string `""` — for a file that was just pushed and
  isn't indexed yet, or when looking directly at a bare commit sha (an intermediate commit
  in history, etc.)**
- **Directories**: always `""` (nothing to copy)

The index is read exactly once per tree listing.

## 8. What We Lost and Its Replacement

What UX is lost by retiring `exports/`, and its replacement:

| Lost | Replacement |
|---|---|
| `gcloud storage cp -r gs://…/exports/datasets/ns/name/main/ ./local/` — bulk copy of a whole directory | Run the `gcloud_script` returned by `GET .../gcs/{rev}`. Under the hood it's a sequence of `gcloud storage cp` calls, but the experience of running it stays "one command" |
| A glob such as `gs://…/exports/datasets/ns/name/main/data/*.parquet` | An ordinary shell glob works against `$DEST` after the script runs (since that is a human-readable local layout once copied) |
| Prefix-based selection for BigQuery external tables, e.g. `gs://…/exports/datasets/ns/name/main/data/*.parquet` | The list of `.parquet` file URIs is enumerated in `duckdb_snippet`. Either list the URIs directly in the external table definition, or run the script with `DEST=gs://another-bucket/…` and then point at that prefix (cross-bucket copies are also handled directly by `gcloud storage cp`) |
| A human-readable tree you could browse directly in GCS | The Web UI's file tree (with `gcloud_command`, §7) and the `GET .../gcs/{rev}` response take its place. Browsing directly in the GCS console is no longer possible |

Every case adds the extra step of "call the API once, then run the result." This is
accepted as the cost of no longer duplicating the real copy inside the bucket.

## 9. Infrastructure (`infra/main.tf`; already applied)

- `soft_delete_policy` and `versioning { enabled = true }` apply to the whole bucket. There
  is **no** age-based noncurrent lifecycle rule — deletion of `lfs/` and `blobs/` is left
  entirely to reference-counting GC (§5). An object untouched for 90 days is, in most
  cases, exactly the kind of stable dataset real copy that ought to keep being served, so
  age alone is not a valid reason to delete it
- The only remaining age-based lifecycle rule is on `tmp/uploads/` (deleted after 1 day by
  default — reclaiming orphans left by failed proxy uploads), unrelated to `lfs/` / `blobs/`
- There is no longer a lifecycle rule dedicated to `cache/blobs/` (as noted in §2, it has
  been folded into `blobs/`)
- Read IAM follows the predecessor design: `roles/storage.objectViewer` is granted across
  the whole bucket (`google_storage_bucket_iam_member.bucket_readers`,
  `var.bucket_reader_members`). We deliberately **do not** scope this to a prefix via an
  IAM Condition — `storage.objects.list` is evaluated against the bucket as a whole, so
  adding `resource.name.startsWith(…)` would break enumeration for both
  `gcloud storage cp -r` and BigQuery external table scans. Defense instead relies on "not
  handing out roles that include `storage.objects.delete` to humans," backed by the two
  layers of `soft_delete_policy` plus versioning

## 10. Retired Mechanisms (a record of decisions from the predecessor design)

A record of the mechanisms in `docs/single-copy-storage-design.md` that **no longer need
to exist** now that the concept of `exports/` itself is gone.

- **Computing an oid's home (`PreferredLFSHome`) and repointing
  `lfs_objects.storage_key`**: this was needed because the real copy's location shuttled
  between `exports/` and `lfs/` depending on "is it on the default branch or not." Now that
  the real copy's location is determined by the oid alone, the operation of "compute a
  home and move to it" doesn't exist at all
- **`vacateExportKey` / `relocateIfHome` — evacuation before overwrite/delete**: complexity
  that arose because the `exports/` key was not scratch space but the real copy itself.
  Every push that wrote different content to some path had to reverse-look-up "is this key
  someone's real copy," and evacuate it before overwriting if so. Content-addressed keys
  are immutable by definition, so the operation of "overwriting" never happens in the
  first place
- **Ordering guarantees for copy → DB update → delete (the crash-resilience table in
  §8)**: this fixed an ordering — "copy to the new key first, then repoint the DB pointer,
  and only then delete the old key" — so that a crash mid-move from key A to key B would
  never leave reads broken. Since the real copy no longer moves between keys at all, this
  procedure disappears entirely
- **`storage_reclaim_jobs` (asynchronous cleanup after repository deletion)**: because
  deleting the `exports/` tree could implicate the LFS real copies, it had to be split off
  into an asynchronous job separate from deleting the repository row. Now that deletion
  never touches GCS at all, deleting a repository is complete once the DB row, the bare
  repository, and the WAL are deleted (`deleteRepo` in `internal/api/repos.go`)
- **The `relocate_exports` transfer job**: see `docs/dev/repo-transfer-design.md` §10. Now that
  transfers no longer change GCS keys, the concept of a relocation job disappears entirely
- **`thinkingface verify-exports`**: a command that cross-checked `repo_files` against the
  `exports/` layout for consistency. Now that `exports/` — "the second layout that needed
  cross-checking" — is gone, it's unnecessary. Only `thinkingface gc` (reference-count-based
  deletion) remains

## 11. Migration

**Because this targets production readiness, there is no consideration for backward
compatibility with existing data.**

- At the time this design landed, the change was a new sequentially numbered migration file
  applied as a diff on top of the existing schema (§3). The migration history has since been
  squashed into a single `0001_init.sql` per dialect (see `CLAUDE.md`), which now simply never
  creates `lfs_objects.storage_key` or `storage_reclaim_jobs` in the first place, rather than
  creating and then dropping them
- Objects remaining under `exports/` and `cache/blobs/` in an existing GCS bucket are
  **not** automatically deleted by this migration. **The operator deletes them manually**
  (`gcloud storage rm -r gs://bucket/exports/` /
  `gcloud storage rm -r gs://bucket/cache/blobs/`). This isn't automated because this
  design was written on the assumption that "the bucket gets rebuilt from scratch"
  (in development, `make down` rebuilds it along with the volume); the operator applying
  this to production should confirm the blast radius themselves before deleting
- For local development (compose), `make down` rebuilding the whole volume is sufficient

## 12. Test Plan

| Target | Contents |
|---|---|
| `internal/syncer` | That `publishBlobs` targets every pushed ref (branches and tags alike), that it skips existing keys via Stat, and that it never deletes anything |
| `internal/store` | Correctness of `ListReferencedLFSOIDs` / `ListReferencedBlobSHAs` / `UntrackedLFSObjects`, and that `DeleteUntrackedLFSObject`'s claim really blocks a concurrent `RecordLFSObject` into `ErrLFSObjectGone` rather than letting it link bytes being deleted. Both the SQLite and PostgreSQL paths (`make test-store-pg`) |
| `cmd/thinkingface` (`gc`) | Orphan detection on both the LFS side and the blobs side, the `blobGrace` / `untrackedLFSGrace` boundaries, that an object reclaimed by the unreferenced pass is not considered again by the untracked one, that the untracked pass never reaches `tmp/uploads/`, and switching between dry-run and real deletion |
| `internal/api` | That the script generated by `GET .../gcs/{rev}` matches the spec byte-for-byte (ordering, escaping, the `DEST` default). That `TreeEntryUI.gcloud_command` is correctly differentiated between an indexed ref and an unindexed rev (e.g. a bare commit sha) |
| `e2e` | `make test-e2e` — that upload → download → clone succeeds. That when two different repositories share a file with identical content, deleting one still leaves the other readable (a regression check for deduplication) |

**The single most important regression**: "repositories A and B share the same file;
deleting A still leaves it downloadable from B." This is the lifeline of content-addressed
sharing, inherited from the predecessor design.

## 13. Alternatives Considered and Rejected

| Alternative | Why rejected |
|---|---|
| Key `exports/` by `storage_path` (keep it immovable on transfer without giving up human-readability) | `storage_path` is a ULID, so as-is it stops being human-readable, defeating the whole point of `exports/`. And if we instead keep a `(ns, name)` reverse lookup for `storage_path` somewhere outside GCS at all times, that ends up being exactly the same shape as "compute it on demand via an API" (§6 of this design) — leaving no reason left to keep the `exports/` layer around |
| Continue the line of `docs/single-copy-storage-design.md` (make `exports/` the real copy, managed via `lfshome`) | As described in §10 "Retired Mechanisms," the essential complexity of the `vacateExportKey` / `relocateIfHome` / `reconcileLFSHome` trio remains. A relocation job is still needed on every transfer. Not worth the implementation and operational cost |
| Keep `exports/` not as the real copy but as a derived mirror (`lfs/` is authoritative, `exports/` is an asynchronously-following cache) | Storage usage doubles again for LFS files (the exact problem the predecessor design was trying to solve recurs). On top of that, a consistency check for "does the mirror match the git state" (equivalent to `verify-exports`) would ultimately be needed again |
| Retire `exports/` and only offer direct HTTP reads (give up on `gcloud storage`) | DuckDB can read `https://storage.googleapis.com/...` via httpfs too, but `gcloud storage cp` and BigQuery external tables assume `gs://` URIs, and there's no substitute along that path.
